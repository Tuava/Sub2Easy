# 账号 401 监控与自动重授权

## 修复验号与启用闭环（续跑更新）

设置 `resume_paused_401`（界面“对已托管的401暂停账号：修复并验号通过后也自动启用”）在新配置中默认开启；已保存的显式 false 不会被覆盖。全局监控初始关闭；可以手动开启并逐号托管，也可在提交部署时确认上线后自动托管。只有 `resume_after_success=true` 且账号有明确401、active/error 状态、已托管、身份一致时，原本暂停的账号才可在凭据更新与SSE验号成功后开启调度。inactive、未知调度状态、普通暂停且无401、验号失败、未知写入结果均不会因此启用。

管理 GET 请求只对网络错误及 408/429/500/502/503/504 最多尝试3次（间隔0.3秒、1秒）；401/403与格式错误不重试。这个重试规则不会作用于 NVT 登录、凭据写入或启停 POST。

自动重授权拿到新凭据后，新增加密续跑记录：

- `apply`：新凭据有效、未发送凭据写入、暂停后的配置和更新时间已记录。
- `verify`：凭据写入有已确认结果，下一步验号/启用。
- 只有已知检查点后的可重试 GET 失败，才安排限次延后续跑；续跑不再调用NVT。超过限额或配置已变化转待办。
- 可点击账号行“续跑验号并启用”，明确确认后按检查点补完；如果之前已修好但保持暂停，则重新验号，通过后启用。
- 原 v0.2 `MONITOR_FETCH_FAILED + 已有有效授权 + confirmed暂停记录 + 无写入意图` 的已知失败可以迁移到 apply 检查点，不重复登录。
- 手动授权、部署与检查点续跑没有历史次数上限；自动重登仍按防循环预算计算。续跑不需要NVT Cookie，但仍要求站点配置、托管、全局监控及绑定一致。
- 对运行中退出、未知写入、配置修订不符、过期授权等无法判断的情况不盲目重放。检查点有效期24小时；停止监控会取消排队续跑，正在运行任务在后续步骤前检查开关。

### 检查点迁移与到期校验

- 有效期在入队和执行前都检查。缺少时间、无效时间、未来时间、超过24小时都停止，不能用当前时间重新开始计时。
- 旧 apply 检查点的时间来自暂停记录所关联的、属于同一账号的终态自动任务；缺少关联任务时不猜测。云端配置与更新时间还要匹配，现存凭据仍要通过有效期和身份检查。
- verify 续跑必须有已确认的凭据写入记录，且云端当前为 active、停止调度。不能仅凭一个“以前成功过”的字符串就入队。
- 新完成的恢复保存配置摘要、验号时间、模型、任务与云端 ID 的证据。后续自动启用前，继续对比该摘要。旧恢复记录如果没有历史配置摘要，只能由用户核对当前配置后显式发起续跑；不能自动迁移。
- 两个恢复开关都允许启用时，才自动迁移旧暂停完成任务；主开关关闭不能被迁移逻辑绕过。
- 没有 NVT Cookie 时仍可轮询、处理已有凭据的续跑，但不能提交新的 NVT 登录。

## 使用步骤

1. 在“连接与模板”保存 sub2api 管理地址、管理员 API Key 和 NVT `scm_session`。
2. 导入对应账号的 `账号----密码----2FA种子`。**只有云端号，没有本地材料，无法自动重新登录。**
3. 在“号池总览”绑定每个账号的原 sub2api ID。程序创建过的云端号已有绑定，无需重复绑定。绑定会校验平台、邮箱和 workspace，不能凭返回文件顺序配号。
4. 点击账号行的“监控”，或多选账号后“开启所选监控”，确认把这些账号交给自动修复。
5. 打开“账号监控”：设置检查间隔、401 等待窗口、恢复验证模型、每小时任务预算和“验证成功后恢复调度”，点击“保存并开启自动监控”。

两级开关分别表示“允许自动系统运行”和“哪些账号允许被修改”。全局开关不会自动接管所有账号，未绑定账号无法启用托管。模型 ID 必须是这些账号确实可用的文本模型；当前手动填写，不猜默认模型。

## 实际执行链

```text
完整拉取 OpenAI 账号列表
  → 已托管、绑定一致、非人工停用、明确账号401
  → 先等待刷新窗口（默认120秒）
  → 若401仍持续，持久化 auto_reauth 任务
  → 再读原账号，确认故障仍在、记录配置与updated_at
  → 记录暂停意图 → 停调度 → 读回
  → 将此账号、密码、2FA种子发往NVT重授权接口
  → 验证sub2json身份 → 确认期间云端无配置/凭据版本修改
  → apply-oauth-credentials 更新原账号ID
  → SSE模型测试（一次小请求）
  → 成功完成事件 + 原账号状态读回
  → 按设置恢复调度，记恢复时间与任务结果
```

“调用 2FA”在这里是调用已经配置的 NVT 接口，`mailbox_credential` 仍传完整三段材料（第三段为种子），不另找一个不明 2FA 服务，也不假设第三段是六位验证码。

首次手动导入/手动授权流程仍保持原来的“手动确认写入、云端保持暂停”行为；**自动修复只更新已绑定的旧号，不自动创建新号或移动分组。**

## 检测来源

本版读取 sub2api 管理接口的账号状态，不轮询浏览器，也不每分钟对每个账号发模型请求。

- error 账号读取 `error_message`。
- active 账号读取仍在有效期内的 `temp_unschedulable_reason`。
- 识别当前研究版本上游写出的 `Authentication failed (401):`、`OAuth 401:`、`OAuth 401 (no refresh_token):`、`Token revoked (401):`、`Unauthorized (401):` 前缀。
- 仅有任意正文包含“401”、已过期的冷却理由、403/429、代理报错或管理员 API 的 401，都不作为账号掉授权事件。
- 某些分支版本使用不同的状态/文案时，可能无法命中；需要增加明确的版本适配，不把所有 error 状态都当 401。
- 没有业务请求、且 sub2api 尚未产生错误状态的静默失效账号不会被主动发现；本版不是全号池周期模型探测器。

### 掉授权与暂停分开判断（修正旧版误判）

旧版先看 `schedulable != true`，把不可调度统一显示成“人工暂停”，会挡住 `status=error + schedulable=false` 的真实401。现在先读取授权故障，再分别判断调度状态：

- `active/error + 明确401 + schedulable=false`：显示红色“401掉授权”，计入需要处理；已托管且无其他阻塞时仍可进入重授权流程，不需要先让失效号接流量。
- 账号原本可调度：由系统暂停后，可按原设置验号恢复。
- 账号原本停止调度：默认仍保持暂停；启用上述 `resume_paused_401` 后，对明确401的托管账号允许修复、验号通过后开启。旧任务已停在“修复但未启用”的，可点“续跑验号并启用”。
- `inactive`：显示“云端已停用 · 不自动处理”，不推断具体由谁操作。
- 没有401且 `schedulable=false`：显示“停止调度 · 原因待确认”，不再称为人工暂停。
- 调度字段缺失、非布尔值或账号状态异常：显示“账号/调度状态未知”；如果另有明确401，仍展示故障，但不执行修改。

排队时保存原调度开关，执行前再次核对；如果排队后人工启停了账号，停止该次任务而不抢回控制。已知修复失败/未知结果的待办继续阻止自动重试，但监控仍读取最新授权故障，让红色状态不会被“需要处理”覆盖。

默认每 60 秒检查，持续 401 等待 120 秒，给内置刷新留出恢复时间。等待不是“已确认原生 refresh 任务失败”的证明，而是观察到同一账号仍有明确 401。错误文案或冷却时间变化不会无限重置等待窗口；正常恢复则清除本次事件。

## 持久化、限额与失败处理

- 复用单 Worker 和进程文件锁，任务增加 `kind`、加密 `context`；已有数据库启动时自动新增列，不删除原账号/配置。
- 同一账号同时只有一个排队/运行任务；同一登录身份不允许多份独立托管，避免同一会话并行轮换。
- 每账号 30 分钟最多 2 个授权任务；全局每小时默认最多 6 个自动任务。计数按已提交任务计算，失败也消耗预算。
- 验证码错误、密码错误、身份不符、响应格式不支持：单账号进入待办，不循环重登。原账号保持暂停。
- NVT Cookie 失效/限流：暂停连接器；更新 Cookie 后才能继续。账号级失败待办不会被更新 Cookie 顺带清除。
- 管理 API 401/403：监控显示管理员认证失败，不把号池内全部账号标坏；完整列表未取得前不生成账号修复任务。
- 登录超时、云端写入超时、测试断流：记录结果未知/待处理。无论错误发生在哪一步，都不在 finally 中盲目开启调度。
- 程序在任务中途退出：原 running 任务重启后变 unknown，不重发；暂停意图保留，账号进入待办。
- 人工修复后，可点账号行“解除待办”。它只读云端确认 active+可调度且无401，再清除本地阻塞，不修改云端。云端写入意图仍未知的情况必须另行对账，不能直接解除。
- 停止监控取消排队中的自动任务；已发出的 HTTP 无法撤回，但会在后续副作用步骤前检查开关，不继续写入/验号/启用。不会自动恢复已暂停账号。

## 保护原配置和人工操作

每次操作核对原 cloud ID、邮箱、workspace、绑定 user_id，拒绝将影子账号作为独立凭据所有者。修改前保存分组、代理、并发、优先级、倍率、运营有效期、模型映射、指纹/部分限额等配置摘要。

暂停后记录 `updated_at`，NVT 返回后及实际凭据写入前再次检查。如果期间发生人工改配置或后台 Token 刷新导致版本变化，停止覆盖并报冲突。指纹 seed、分组、代理、倍率不会由 NVT 返回的默认配置覆盖。

**普通 sub2api 更新接口没有原子的 If-Match/CAS。** 读回校验能发现大多数竞态，但不能消除最后一次检查与远端写入之间的极短窗口，也无法判断“人工把已暂停的账号再次设为同一个值”的意图。托管账号不要同时由另一自动系统写入；手动操作前先停监控。严格多写者场景仍需要上游条件更新接口或共享锁扩展。

SSE测试接口成功时本身可能清理冷却/错误，属于有副作用的操作；不是纯只读探测。测试 HTTP 200 不算成功，必须有完整 `test_complete + success=true`，后续不能有 error。测试失败、账号人工 inactive、配置漂移或仍存在运行态阻塞时，不开启调度。

## 运行条件

后台循环属于 Sub2Easy 服务，不是 Codex 的定时任务。关闭网页不影响它。

**本地服务运行、电脑不休眠、凭据库解锁**时才可执行。锁库、关闭服务、重启或电脑休眠会中断连续监控；重启后输入主密码才恢复。要长期无人值守应使用常在线主机，不能把笔记本休眠期间说成监控正常。

## 验证范围

回归测试覆盖完整恢复、原生恢复后不重登、重复事件、管理员401、删除/人工暂停、小时预算、验证码错误、Cookie失效、未知结果、失败SSE、配置/凭据并发变化、停止监控、重启不重放。

另外使用真实本地 HTTP 模拟 sub2api 和 MockTransport 模拟 NVT，验证后台循环依次产生：停止调度 → 原 ID 凭据更新 → SSE 测试 → 恢复调度，NVT 仅调用一次。未对真实账号做自动修复测试，生产站点开关保持关闭，需用户配置验证模型并选择托管账号后启用。
