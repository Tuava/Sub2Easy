# 给部署方 AI 的操作手册

这是 AI 代理的部署检查单，不是随附凭据。请先读根目录 `AGENTS.md`、README 和 SECURITY.md。本文不能让任何 AI 自动读取用户密码或绕过其工具权限。

## 0. 先确认使用模式，主动提示 NV 站 CK

**必须主动提醒，不能省略：**

> 需要使用账号密码/2FA重授权和自动401修复，请在本地工作台“连接与模板 → scm_session Cookie”填写 NV 站的 CK。CK 不要发到聊天或GitHub；填写后我只检查“已配置/连接器是否暂停”。只有 sub2api 管理员 Key 不够完成 NVT 重授权。

如果用户选择只导入有效 sub2api JSON，可以不配置 CK，但完成报告必须注明“Token-only 模式，完整自动重新登录未就绪”。不要为了让 `has_cookie=true` 而填入示例值。

必须向用户确认/交代以下项目，凭据通过本地密码框输入：

| 配置 | AI 应主动做的事 |
|---|---|
| sub2api 地址 | 确认目标站点和 Admin API 兼容版本，不猜测站点 |
| 管理员 Key | 提醒是管理员 Key，不是普通用户调用 Key |
| **NV 站 CK** | **提醒填写 `scm_session`，区分未配置、已保存、连接器暂停；不要漏掉** |
| 密码/2FA材料 | 说明第三段是完整Base32种子；JSON-only缺失时不能完整重登 |
| 验号模型 | 使用该站账号实际可用的模型ID，不硬编码示例模型 |
| 隔离/生产分组 | 从当前站点下拉读取；确认隔离组不接业务流量 |
| 自动化开关 | 按用户选择开启401托管；团队失效清理默认关闭，需确认移组 |

## 1. 安装与启动

支持 macOS/Linux、Python 3.11+；Node仅用于测试。推荐 git clone，后续可使用内置更新命令。

```bash
git clone https://github.com/Tuava/Sub2Easy.git
cd Sub2Easy
uv sync --locked
uv run --locked sub2easy --data-dir ./data
```

- 用部署环境的持久服务管理器或前台终端保持后端运行；不能只用短命shell的 `&` 然后声称永久后台运行。
- 查看进程与监听端口，确认 `127.0.0.1:8765` 的首页返回200；不要把一次启动日志当作持续存活。
- 让用户使用启动器生成的完整本机链接；不要公开带 `#token` 的URL。页面会自行移除fragment并保存标签页会话。
- 主密码在本地设置/解锁。不能通过新建空库、尝试猜密码来绕过旧库锁定。
- 远程机器仍只绑定loopback。可建立 `ssh -L 8765:127.0.0.1:8765 HOST`，在本地访问；不要改公网绑定或把管理员服务暴露出去。

## 2. 配置检查（不泄漏凭据）

解锁后，使用现有本机会话读取 `/api/state` 的布尔值：

- `settings.has_admin_key`、站点地址：可配置是否已保存。
- **`settings.has_cookie`：未保存必须主动提示补 NV 站 CK。**
- **`settings.connector_paused`：暂停必须提示更新/核对 CK、会话或限流原因。**
- 账号的 `has_login_material`：无材料不能完整重授权。
- `monitor.config.enabled` 与逐号 `monitor.enabled`：两级都要核对，不把“托管勾选”当后台一定运行。

这些字段不证明上游凭据有效。未经用户明确要求，不调用真实登录/验号来“测试CK”，尤其不要重复登录同一个账号。

## 3. 部署验收

- 启动版本正确、服务持续监听、页面可访问；凭据库状态正确。
- NVT模式：主动提醒CK已完成；已配置但未验证时如实注明。Token-only模式：明确自动重新登录不可用的缺项。
- 批量导入结果在同页显示完整邮箱和云端ID；明确区分仅本地、排队、验号、上线。
- 真正上线必须完整SSE成功、身份和配置一致、最终active/schedulable读回。不可仅凭HTTP200宣称恢复。
- 用户选择的监控、生产组、并发上限符合预期；不得擅自修改真实账号来追求绿色状态。

## 4. 更新流程

先看 [updates.md](updates.md)。默认跟随官方 **main分支**，不是尚未发布的稳定Release。GUI“连接与模板 → 版本与更新”可检查并生成含实际数据目录的命令。

```bash
# 只检查，不安装，不提交账号材料
uv run --locked sub2easy-update
# 暂停新任务，等待任务结束，停止后端后，在同一git目录执行
uv run --locked sub2easy-update --apply --yes --data-dir ./data
# 更新完成，用同一数据目录重启
uv run --locked sub2easy --data-dir ./data --reuse-session
```

更新器检查main/官方origin/工作区干净，持有数据目录进程锁，备份SQLite（含WAL内容），仅快进到检查过的提交，执行 `uv sync --locked`。本地改动/分叉不强推、不自动stash。依赖失败尽力回滚源提交和依赖，失败则报告需要人工核对；数据库备份不自动覆盖原库。

ZIP/wheel安装不会假装有git；请在另一目录下载/构建检查后的新版包，停服务、备份、升级，并沿用原数据目录。不要删除data，不要重新导入来代替迁移。

**更新完成还要再提醒一次：** NV站CK保存在旧库里，应该继续存在；检查 `has_cookie` 与 `connector_paused`。若为空或暂停，主动提醒用户在本地界面补/更新CK，不能只报“新版本已启动”。

## 5. 完成报告模板

```text
版本/安装方式/数据目录：已核对（不含完整启动令牌）
本地服务：持续运行 / 阻塞原因
sub2api管理员连接：已配置 / 缺失 / 未验证
NV站CK：未配置需填写 / 已保存未验证 / 已暂停需更新
登录材料：完整 / Token-only缺少密码或2FA
自动401恢复：已开启并托管N个账号 / 未开启 / 尚缺配置
真实部署验收：未执行 / 通过 / 具体失败阶段
```

不要在此报告包含真实CK、Token、主密码、账号密码或2FA种子。
